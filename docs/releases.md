# Releases

Releases are prepared automatically with [release-please](https://github.com/googleapis/release-please).
The versioning strategy is the same for the whole monorepo; see [versioning.md](versioning.md).

## What is configured

- `.github/workflows/release-please.yml` — a workflow on push to `main` with `contents: write`
  and `pull-requests: write` permissions (plus `issues: write` for labels). It passes
  `token: ${{ secrets.RELEASE_PLEASE_TOKEN || secrets.GITHUB_TOKEN }}`: if a PAT is present, the
  Release PR is created with it; otherwise the workflow stays secret-free and uses the built-in
  `GITHUB_TOKEN`.
- `release-please-config.json` — a single `"."` package with `release-type: node` and
  `include-component-in-tag: false`, so tags look like `vX.Y.Z`, not `cal-clone-vX.Y.Z`.
  `extra-files` lists every workspace manifest with the JSON `$.version` updater.
- `.release-please-manifest.json` — the current project version; release-please updates it in the
  Release PR.
- `scripts/check-release-please.mjs` — an offline consistency check of the configuration (part of
  `mise run check` via `check:release-please`).

## How a release happens

1. A commit with a Conventional Commit message lands on `main` (the `commit-msg` hook checks the
   format).
2. The workflow opens or updates the Release PR `chore(main): release X.Y.Z`. The PR changes:
   - `version` in the root `package.json`;
   - `version` in every workspace package listed in `extra-files`;
   - `.release-please-manifest.json`;
   - `CHANGELOG.md` (created on the first release).
3. Merging the Release PR → release-please creates a GitHub Release and the `vX.Y.Z` tag.
4. `mise run check` verifies that the manifest version matches the root and that `extra-files`
   covers every workspace package from `pnpm-workspace.yaml`.

The Release PR is updated on new commits and stays open until it is merged — a release is not
created on every push.

## Commit types and versioning

Release-please uses Conventional Commits and default (SemVer) versioning:

| Commit | Version | CHANGELOG |
| --- | --- | --- |
| `feat: ...` | minor (`1.0.0` → `1.1.0`) | Features |
| `fix: ...` | patch (`1.0.0` → `1.0.1`) | Bug Fixes |
| `perf: ...` | patch | Performance Improvements |
| `revert: ...` | patch | Reverts |
| `<type>!: ...` or the `BREAKING CHANGE:` footer | major (`1.0.0` → `2.0.0`) | Breaking Changes |
| `docs`, `style`, `refactor`, `test`, `build`, `ci`, `chore` | no release | hidden |

A breaking change triggers for any type, including hidden ones: `chore!: ...` produces a major.
If only non-release types landed between releases, no Release PR is created.

## Rules

- Versions are not edited by hand: release-please updates the root version and workspace package
  versions.
- A new workspace package must be added to `extra-files`. Both `check:versions` (version
  mismatch) and `check-release-please` (compares `extra-files` with `pnpm-workspace.yaml`) catch
  this.
- `bootstrap-sha` is only needed for the first run: it bounds the history included in the first
  CHANGELOG. It can be removed after the first Release PR is merged.
- `CHANGELOG.md` is generated by release-please — do not edit it by hand.
- For a non-standard release, use the `Release-As: X.Y.Z` footer in the commit; this is an
  exception, not the everyday approach.

## Token and branch protection (required for auto-merging Release PRs)

`main` is protected: the required `check` check runs in strict mode, and admins do not bypass
protection either (see [ci.md](ci.md)). GitHub **does not run** other workflows for events created
by the built-in `GITHUB_TOKEN` (recursion protection). Therefore a Release PR opened by
`GITHUB_TOKEN` will not get the required `check` check and cannot be merged.

To let the Release PR pass CI and be merged, configure a repository fine-grained PAT:

1. Create a PAT with `contents: write` and `pull-requests: write` permissions (scope — this
   repository only).
2. Save it in the `RELEASE_PLEASE_TOKEN` secret
   (Settings → Secrets and variables → Actions → New repository secret).
3. The workflow will pick it up automatically via
   `token: ${{ secrets.RELEASE_PLEASE_TOKEN || secrets.GITHUB_TOKEN }}`.

Without a PAT the workflow still runs secret-free and opens a Release PR with `GITHUB_TOKEN`, but
such a PR will not trigger `check`. In that case there is only one path: the owner manually adds
a bypass for Release PRs in branch protection settings. This is a deliberate compromise, not the
recommended mode: no secret is added to `check.yml`, and fork PRs stay safe.

Also enable “Allow GitHub Actions to create and approve pull requests”
(Settings → Actions → General), otherwise the Release PR will not be created even with a PAT.
