# CI pipeline

Every push and pull request runs one shared workflow: `.github/workflows/check.yml`
(workflow name `check`). Feature tickets do not add their own CI — they extend this
pipeline. `.github/workflows/hexlet-check.yml` is generated by Hexlet and must not be
edited. Releases are automated separately on push to `main` by
`.github/workflows/release-please.yml` (see [releases.md](releases.md)); it is not part of
the PR check pipeline. An advisory AI review (`review.yml`) also runs on eligible pull
requests; it is not a CI gate and not a required check (see
[Independent AI pull request review](#independent-ai-pull-request-review-reviewyml)).
A scheduled Lighthouse audit (`lighthouse.yml`) reviews the deployed application daily and
is independent of pushes and pull requests (see
[Scheduled Lighthouse audit](#scheduled-lighthouse-audit-lighthouseyml)).

## What the pipeline does

The workflow has three independent jobs.

### `check` (push and pull request)

1. `actions/checkout` — checks out the pull request merge commit on `pull_request`
   (and the pushed commit on `push`); no repository secrets are used. The author's exact
   head is verified separately by `head-browser-evidence`.
2. `jdx/mise-action` — installs the pinned toolchain from `mise.toml`
   (Node, pnpm, hk, pitchfork, actionlint).
3. `mise run setup` — `pnpm install` + `pnpm generate:api` (TypeSpec → OpenAPI → SDK).
4. `pnpm exec playwright install --with-deps chromium` — the browser for the browser scenarios.
5. `mise run check` — the same gate developers run locally.

### `head-browser-evidence` (pull request only)

This job checks out `github.event.pull_request.head.sha` explicitly, records the actual
`git rev-parse HEAD` in `head-sha.txt` and fails if it differs from the expected head. It
installs the same toolchain and dependencies, then runs the owner booking-delete scenario
(`e2e/booking-delete.spec.ts`) and the adjacent guest golden path
(`e2e/golden-path.spec.ts`) against the real backend and frontend. Trace recording is
enabled explicitly (`--trace on`) so successful runs are evidence too.

The job uploads the `head-browser-<sha>` Actions artifact with the recorded SHA, Playwright
JSON results and traces. This artifact is the pre-merge evidence for the author's head:
download it from the workflow run, compare `head-sha.txt` with the current PR head, and open
the trace before merging. A new push produces a new run and a new artifact; an older
artifact still belongs to its old SHA and must not be reused. The job needs no repository
secrets, and the advisory AI review may run before the artifact exists — a human owns the
final SHA check.

The same two scenarios also run inside `mise run check`, which checks out the pull-request
merge commit. The separate job repeats them on purpose: the extra value is the SHA-bound
artifact with traces for the main and adjacent scenario, not additional coverage. The
duplicate Playwright time is accepted as the price of that evidence.

The JSON reporter writes `results.json` through `PLAYWRIGHT_JSON_OUTPUT_NAME=results.json`
with `PLAYWRIGHT_JSON_OUTPUT_DIR` set to the artifact directory, as documented for the
[Playwright JSON reporter](https://playwright.dev/docs/test-reporters#json-reporter). A
`test -s` step fails the job if the file is missing, so the artifact always carries the
machine-readable result next to `head-sha.txt` and the traces.

Changes to this job follow the workflow-file boundary: the OpenCode App cannot push
`.github/workflows/**`, so the agent reports the change and a maintainer commits it.

### `docker` (pull request only)

The third job installs the same mise toolchain and runs `mise run docker:build`
(`docker build --tag cal-clone:local .`). It guards the production artifact — `Dockerfile`,
`.dockerignore`, `docker-entrypoint.sh` and the same-origin SPA build — which the `check`
gate never touches. It runs on pull requests only and is not part of `mise run check`:
the image build takes several minutes and would slow down the main gate.

`mise run check` fans out to:

| Task        | What it proves                                                        |
| ----------- | --------------------------------------------------------------------- |
| `lint`      | oxlint (type-aware for the backend) passes for every package, plus `e2e/`, `playwright.config.ts` and `scripts/`. |
| `typecheck` | `tsc` passes for backend, frontend (`tsc -b`), the API client, and the `e2e/` files (`tsconfig.e2e.json`). |
| `test`      | backend unit tests, backend e2e tests, then frontend component tests. |
| `e2e:golden` | the real-server browser scenarios: owner booking deletion and the guest golden path, against a dedicated SQLite database; the booking API is never mocked. |
| `build`     | backend (`nest build`) and frontend (`vite build`) compile.           |
| `check:sdk` | regenerating the SDK produces no diff (generated artifacts are fresh).|
| `check:versions` | every workspace package uses the root `package.json` version.       |
| `check:release-please` | release-please config: one root package, manifest version matches the root, every workspace manifest is in `extra-files`. |
| `check:ci`  | CI config invariants (`scripts/ci-config.test.mjs`) + `actionlint`.   |

Each task exits non-zero on failure, `mise` propagates a failed dependency, and the
workflow step fails with it. A green job therefore means every gate passed.

The workflow runs with `permissions: contents: read`, has no `secrets.*` references,
and is safe for pull requests from forks.

## Comment-driven agent (`opencode.yml`)

`.github/workflows/opencode.yml` runs OpenCode inside Actions: a comment that contains
`/oc` or `/opencode` — in an issue, in a pull request thread, or on a specific diff line —
starts a run that answers in the same thread and, when asked, pushes a branch or opens a
pull request. It is not part of the PR gate; a run only ever starts from a comment.

- **Triggers:** `mentions: /oc,/opencode`; only those two phrases start a run.
- **Who can trigger it:** `issue_comment` and `pull_request_review_comment` (`created`)
  only, and only with `author_association` `OWNER`, `MEMBER` or `COLLABORATOR`; comments
  from `Bot` users are ignored explicitly. The repository is public and every run spends
  credits on the API key. For `pull_request_review_comment` GitHub takes the workflow
  definition from the base branch and the run only starts from a trusted comment, so a fork
  cannot alter the workflow or start a run, and the secret is never exposed to a fork's own
  workflow.
- **Two jobs, two permission sets:** `budget` and `opencode`; the second one runs only when
  `needs.budget.outputs.allowed == 'true'`.
  - `budget` is the only job with a write-scoped workflow token (`contents: read`,
    `actions: read`, `pull-requests: write`). It checks out the **default branch**
    explicitly (`ref: github.event.repository.default_branch`), because
    `pull_request_review_comment` would otherwise check out the pull request merge ref and
    run pull-request-controlled JavaScript — `scripts/opencode-budget.mjs` included — while
    holding a token that can write pull request comments. `contents: read` covers that
    checkout, `actions: read` lets it list workflow runs, and the write scope posts one
    sticky budget notice.
  - `opencode` checks out the pull request content and holds `contents: read` +
    `id-token: write` only. It has no write scope and the agent never receives the workflow
    token (no `GITHUB_TOKEN`/`GH_TOKEN` in its environment); write access still comes from
    the OpenCode GitHub App over OIDC.
- **Sharing:** sessions are not published — `SHARE: 'false'`. The action's deprecated
  `share` input is ignored by the pinned version, so the decision is expressed as an
  environment variable.
- **One run per task:** `concurrency.group` is the issue/PR number and
  `cancel-in-progress: false`, so a second comment on the same task queues behind the
  running one instead of overlapping it or killing a run mid-push.
- **Limits:** `timeout-minutes: 60`; `fetch-depth: 1`; `persist-credentials: false`; one
  attempt budget per pull request (`OPENCODE_PR_ATTEMPT_BUDGET`).
- **Workflow files are read-only for the agent:** `OPENCODE_PERMISSION` denies `edit` for
  `.github/workflows/**`, because the App push would be rejected (see
  [App permissions](#attempt-budget)). A CI change the agent considers necessary is
  reported in its comment and applied by a human; otherwise the agent spends the whole run
  and fails at `git push`, losing the final commit.
- **Model:** `opencode/deepseek-v4.1-flash` (provider `opencode`, OpenCode Console) with
  `variant: low` for reasoning effort — a comment run stays fast and cheap. The model also
  accepts `high` and `max`; switch to `opencode/deepseek-v4-pro` if a task needs it.
- **Pinning:** `actions/checkout` and `anomalyco/opencode/github` are pinned to full commit
  SHAs with the release tag in a trailing comment, and `VERSION` pins the CLI binary the
  action downloads to that same release. Update all three together.

### Attempt budget

A pull request gets `OPENCODE_PR_ATTEMPT_BUDGET` model attempts (currently `3`). The
budget is derived from the GitHub Actions run history of this workflow; there is no
separate ledger, database, artifact or workflow.

- **Attribution:** `run-name` is `opencode ref-<number>`, where `<number>` is the pull
  request number for `pull_request_review_comment` and `github.event.issue.number` for
  `issue_comment`. Lists of Runs for `issue_comment` do not expose the pull request, so the
  run name is the only reliable link. The gate only applies to pull requests; an `/oc`
  comment on a plain issue is not budgeted.
- **Counting:** a run counts when its `display_title` is exactly `opencode ref-<PR>`, its
  status is `in_progress` or `completed`, its conclusion is not `skipped`, and it was
  created after `max(PR created_at, now - 90 days)`. The number of attempts is the sum of
  `run_attempt`; the current run is excluded and `run_attempt - 1` is added, so a re-run
  is counted too. A completed run counts even when it was cancelled, timed out or failed.
  A run that is still queued is not counted yet; it counts when it starts.
- **Decision:** `used < budget` allows the run. The gate runs in the `budget` job before the
  model job and writes `allowed`; the `opencode` job only runs when
  `needs.budget.outputs.allowed == 'true'`.
  Any error while reading the API, resolving the pull request or parsing the budget is a
  `budget_check_error`: the job fails and the model is not called. If the current run is
  already visible in the history and its `display_title` does not match the expected tag,
  the gate also fails closed instead of silently starting an unlimited budget.
- **Notice:** when the budget is exhausted the gate posts or updates one sticky comment
  (`<!-- opencode-budget-notice -->`) with `limit_exhausted`, the attempt number, the PR
  head SHA, a link to the current run and `needs human` («нужен человек»). A failed check
  publishes the same comment with `budget_check_error`. No label is added, and nothing can
  reset the budget from a comment.
- **Re-runs and cancellation:** a GitHub re-run starts the job from its first step, so the
  gate re-evaluates and the new `run_attempt` is counted. A manual cancellation or a
  timeout is recorded as `cancelled`/`timed_out` and also counts. `concurrency` is
  unchanged, so one attempt per task runs at a time.
- **Window:** Actions run history is subject to the repository retention setting
  (90 days on GitHub). The budget therefore cannot see attempts older than that. Runs
  created before the `run-name` rollout are not tagged and are not counted; the budget
  starts with the first tagged run.
- **App permissions:** the public App metadata (`GET /apps/opencode-agent`) lists
  `actions: read`, `contents: write`, `issues: write`, `metadata: read` and
  `pull_requests: write`. **There is no `Actions: write`**, so the agent cannot delete,
  cancel or re-run workflow runs with the App token; the run history is the authoritative
  record. **There is no `Workflows: write` either**, and an installation can only narrow
  the permissions the App requests, so the App can never push a change under
  `.github/workflows/**`: GitHub answers
  `refusing to allow a GitHub App to create or update workflow ... without 'workflows' permission`
  and the entire push is rejected. That is why `opencode.yml` denies `edit` for that path
  instead of letting the run fail at the last step. Re-check this after App permission
  changes. The workflow token's `pull-requests: write` exists only in the `budget` job,
  which runs the default-branch script; the `opencode` job has no write scope and never
  receives that token.

Limitations of this simplified approach:

- the limit is per pull request; `/oc` on a plain issue is not limited;
- a new pull request starts a new budget;
- the gate is not an atomic counter: `concurrency` and counting `in_progress` runs are the
  serialisation, and an API lag can, in a rare race, let two attempts start together;
- renaming the workflow or changing `run-name` resets the history-based budget (the guard
  tests in `scripts/ci-config.test.mjs` catch this);
- more than 1 000 workflow runs in the window fail closed instead of guessing;
- the budget counts attempts, not tokens: one allowed attempt can still spend a lot;
- blocked attempts also count, so raising the constant may not immediately free attempts;
- the sticky comment is writable by the App; only the Actions history and the step summary
  are the authoritative trail.

### Failure diagnosis

There is no separate result reporter. A failed, cancelled or timed-out attempt is diagnosed
from the Actions run: the run link in the budget notice, the failed step and the step summary.
The `Check the model key` step runs before the agent and fails early with an explicit error
when `OPENCODE_API_KEY` is missing, so the log points at the real cause instead of an unclear
agent failure. The next action is chosen by a human; nothing retries the agent automatically.

Prerequisites — one-time, done by the repository owner:

1. Install the GitHub App on the repository: <https://github.com/apps/opencode-agent> →
   *Install* → select this repository. Without the installation the OIDC token exchange
   fails and the run stops right after checkout.
2. The `OPENCODE_API_KEY` Actions secret must exist (*Settings → Secrets and variables →
   Actions*). It is already stored in this repository; the value never goes into a commit,
   a workflow file or a comment.

Check both without revealing the value:

```bash
gh api repos/{owner}/{repo}/actions/secrets/OPENCODE_API_KEY --jq '.name'
```

The secret check prints only the name. For the App, open
`https://github.com/juliastetskaya/ai-for-developers-project-387/settings/installations`
(Settings → GitHub Apps) and look for `OpenCode Agent`; the App listings API
(`GET /repos/{owner}/{repo}/installation`) only answers to an App JWT, so a missing
installation shows up as a run that stops at the token-exchange step.

## Automatic issue triage (`issue-triage.yml`)

`.github/workflows/issue-triage.yml` triages every newly opened issue: OpenCode reads the
issue, the repository docs and the relevant code, and posts one structured comment with the
request summary, expected behaviour, existing functionality, open questions, risks and an
initial scope. It never writes code or creates specifications or tickets; a human approves the
behaviour before `/to-spec` and `/to-tickets` run.

- **Trigger:** `issues`, `types: [opened]` only — comments, edits and label changes do not
  re-run it.
- **Who:** `author_association` must be `OWNER`, `MEMBER` or `COLLABORATOR`, and
  `issue.user.type` must not be `Bot`. Enforced in the job-level `if` on the event payload.
- **Generated issues:** skipped when they already carry `ready-for-agent`, the triage label
  both skills apply when they publish a spec or a ticket. App-created issues are also caught
  by the bot filter.
- **Permissions:** `contents: read` + `id-token: write`. The triage comment is posted by the
  OpenCode GitHub App over OIDC; `GITHUB_TOKEN` gets no write permissions.
- **Limits:** `timeout-minutes: 15`; concurrency group `issue-triage-<issue number>` with
  `cancel-in-progress: false`; `OPENCODE_PERMISSION` denies `edit` and `external_directory`.
- **Report marker:** the report carries the hidden marker `<!-- issue-triage-report -->` so
  later automation can recognise it. No duplicate guard is needed: the workflow runs only on
  `opened`, before any triage comment can exist.

## Independent AI pull request review (`review.yml`)

`.github/workflows/review.yml` runs an independent OpenCode reviewer on eligible pull
requests and publishes **one advisory comment** with the reviewed commit SHA. It does not
approve, request changes, merge or edit anything, and it is deliberately **not** a required
status check or a branch-protection context. A human still owns the review and merge
decision.

The reviewer's criteria, severity levels and report format live in [`REVIEW.md`](../REVIEW.md).
The PR template (`.github/pull_request_template.md`) asks for the context, tests, risk and
rollback information the review needs.

- **Triggers:** `pull_request` with `opened`, `synchronize`, `reopened`,
  `ready_for_review` and `edited` (only when the PR body changes). The workflow never uses
  `pull_request_target`.
- **Eligible PRs:** same-repository PRs from `OWNER`, `MEMBER` or `COLLABORATOR` authors,
  plus the repository's `opencode-agent[bot]`. Drafts and fork PRs are skipped by the job
  `if`, so a fork PR never reaches the secret or the reviewer.
- **One run per PR:** the concurrency group is the PR number and `cancel-in-progress: true`,
  so a push supersedes an older review instead of publishing a stale result.
- **Two jobs, two permission sets:**
  - `review` checks out the PR head commit (`fetch-depth: 0`, `persist-credentials: false`),
    reads the PR/issue/CI context with read-only permissions (`contents`, `issues`,
    `pull-requests`, `actions`, `checks`, `statuses`) and runs OpenCode. It has no GitHub
    write permission.
  - `publish` downloads the report artifact and posts or updates the comment with only
    `pull-requests: write`. The OpenCode process never receives that token.
- **Reviewer capabilities:** OpenCode starts with `"*": "deny"` and allows only local
  `read`, `glob`, `grep` and `list`. `bash`, `edit`, `task` (delegation), `webfetch`,
  `websearch`, `skill`, `lsp`, `todowrite`, `question`, `external_directory` and
  `doom_loop` are denied. The repository's `opencode.json` is not loaded, external plugins
  are disabled (`OPENCODE_PURE`), Claude instruction files/skills are disabled, and the
  Hexlet and Render MCP servers are therefore unavailable.
- **Base criteria only:** OpenCode reads `.review/review-criteria.md` and
  `.review/agents.md`, copied from `REVIEW.md` and `AGENTS.md` at the base commit. The
  workflow never falls back to the PR head and removes head copies of
  `REVIEW.md`/`AGENTS.md`/`CLAUDE.md`/`CONTEXT.md` before the model starts. If either base
  file is missing or empty, the review fails with an error and no model call is made.
- **Version and model:** the workflow installs the pinned V1 CLI with
  `VERSION: 1.19.6` (the installer refuses a 2.x release), checks
  `opencode --version`, and runs `opencode/deepseek-v4.1-flash` with `variant: low`. The same
  version and model are used by the manual `/oc` workflow and by issue triage. The review
  job calls `opencode run` directly because the OpenCode GitHub Action only supports
  `issue_comment` and `pull_request_review_comment` events, not `pull_request` lifecycle
  events.
- **Issue context:** the review collects both `closingIssuesReferences` and issue
  references from the PR description (`#123`, `owner/repo#123` and GitHub issue URLs). It
  fetches the available issue body and first comments. References from external
  repositories are attempted and, when the workflow token cannot read them, are explicitly
  marked as unavailable with a direct link. At most ten references are fetched per review,
  and the combined issue context is capped at 60 KB.
- **Untrusted input:** the prompt treats the repository, PR description, linked issue,
  comments and diff as data, not instructions. The report is emitted through
  `--format json` and parsed locally; the workflow adds the hidden marker
  `<!-- ai-review-report -->` when publishing. Tracked symlinks are removed before OpenCode
  starts, so PR content cannot redirect file reads outside the checkout.
- **Publication:** the advisory comment includes the reviewed commit SHA and a link to the
  exact GitHub Actions run. The publish job looks for an existing `github-actions[bot]`
  comment carrying the marker and PATCHes it; it creates a comment only when none exists. A
  short result and the comment link are also written to `$GITHUB_STEP_SUMMARY`.
- **CI is context, not rerun:** the review job calls read-only `gh pr checks` and includes
  the current results in the prompt. It never runs `mise run check`, the test suites or the
  Docker build. If CI is pending or failing at review time, the report should say so.
- **Boundaries:** the reviewer cannot call GitHub, run shell commands, use the network,
  launch subagents, edit files or write to the PR. It is an advisory signal only.

### Validate the review workflow

```bash
mise run check:ci   # guard tests in scripts/ci-config.test.mjs + actionlint
```

The guard tests assert the event filter, the absence of `pull_request_target`, SHA-pinned
actions, the V1 CLI version and model, the deny-by-default permission object, the split
between review and publish, the artifact hand-off, the marker and the PATCH/POST paths.
They also cover the run link, the step summary, issue references from the PR description,
the explicit external-issue marker and the no-fallback base criteria. They cannot prove
runtime behaviour (token scoping, comment publication, the model's response or concurrency).
Exercise those on a real same-repository PR:

1. Open a draft PR from a branch in this repository and confirm no review runs.
2. Mark it ready and confirm one comment appears with the current head SHA and an Actions
   run link; the job summary shows the same brief result.
3. Push another commit and confirm the same comment is updated, not duplicated.
4. Edit the PR body to reference another issue and confirm the review re-runs with that
   issue's context; reference an inaccessible external issue and confirm it is marked
   unavailable.
5. Open a fork PR and confirm the review job is skipped and no secret is used.
6. On a test branch, temporarily remove `REVIEW.md` or `AGENTS.md` from the base and confirm
   the review fails with an error before any model call.
7. Check that the comment is not a required status check and does not block merging.

## Scheduled Lighthouse audit (`lighthouse.yml`)

`.github/workflows/lighthouse.yml` audits the deployed application once a day, asks OpenCode
to find genuinely actionable problems and publishes a small number of deduplicated issues.
It is not part of the PR gate and never runs on a push or a pull request.

- **Triggers:** `schedule` (daily, `13 10 * * *`) and `workflow_dispatch`. A scheduled run
  always uses `test_mode=false`; the manual run can enable the demonstration described below.
  The workflow only exists on the default branch, so a schedule starts after the file is
  merged into `main`.
- **Target:** `vars.APP_URL`, the deployed application (currently
  `https://cal-clone-gqib.onrender.com`). The variable is a repository variable, not a secret.
  Only `/` is audited, mobile preset, `lighthouse@12.8.2` (Lighthouse 13 needs Node 22.19+ and
  `mise.toml` pins 22.16.0). The job fails early when the variable is missing or is not an
  `https://` URL.
- **Warm-up:** the free Render plan sleeps after idle time; the first request can take a
  minute. The audit job polls `/health` for up to ten minutes and issues three requests before
  Lighthouse starts, so a cold start does not become a fake performance finding.
- **Validity gate:** before the model sees anything, the audit is rejected when it reports a
  `runtimeError`, a 5xx request, a page that loaded almost nothing, a missing LCP metric or a
  final URL outside `APP_URL`. A broken deployment must not produce invented issues.

### Jobs and permissions

The workflow declares `permissions: {}` and scopes every job:

| Job | Permissions | What it does |
| --- | --- | --- |
| `audit` | `contents: read` | normalises the run mode once, warms the app, runs Lighthouse, records hashes, uploads the reports |
| `analyse` | `contents: read` | verifies the report hashes, builds the digest, writes the prompt, hashes both inputs and runs OpenCode; no GitHub token reaches the model |
| `publish-preview` | `contents: read`, `issues: read` | always runs, including dry runs: reads existing issues, classifies findings, writes `decisions.md`, `proposed-issue.md`; never writes to GitHub |
| `publish-create` | `contents: read`, `issues: write` | runs only when the normalised `create_issues` output is `true`; re-checks deduplication immediately before each `gh issue create` |

`test_mode` and `create_issues` are normalised in the first step of `audit` and exposed as job
outputs (`needs.audit.outputs.*`). `$GITHUB_ENV` does not cross job boundaries, so no
downstream job reads the raw event payload. `GITHUB_EVENT_NAME` is passed explicitly to every
downstream job because the scripts enforce the dispatch-only test-mode guard themselves.

Every job checks out `github.event.repository.default_branch`: the audit targets the deployed
build, and the scripts that consume the API key or a write token must be the trusted
default-branch versions rather than a copy from the dispatched branch.

### Reports, hashes and the model input

- Lighthouse writes `landing.report.json` and `landing.report.html` under `reports/`.
- `record` writes `reports/meta.json` with the sha256 and size of every report.
- `analyse` verifies those hashes before building the context, and `build` verifies them again
  after writing `context.md`: a digest that modifies a report fails the job before the model is
  called. The same check runs in `scripts/lighthouse-digest.test.mjs`.
- `context.md` is a digest, not the raw report: category scores, core metrics, failing
  machine-readable audits with their evidence and potential savings, and failing requests.
  `manual`, `informative` and `notApplicable` audits never reach the model.
- The prompt is written to `prompt.md`. Immediately before the CLI call, `provenance.json`
  records the sha256 and size of `context.md` and `prompt.md`, the event, the mode flags, the
  model, the variant and the Lighthouse version. Both files stay in the analysis artifact. The
  hashes are a reproducible record of the CLI inputs — they are not proof that the provider
  received those bytes. The response is recorded as raw `events.jsonl`, decoded to `report.md`
  and reduced to `findings.json`.
- `build` also writes `audits.json`, the machine-readable scope of the run (audited route
  pathnames and failing audit ids). It is uploaded with the analysis artifact and used by the
  publishing jobs to reject a finding the model invented.

### Publishing and deduplication

- The fingerprint is derived from the route, the audit id and the scope (resource path with
  content hashes normalised, DOM selector without positional pseudo-classes, or the audit id).
  Scores, savings and dates are excluded. It is stored in a hidden marker in the issue body
  (`<!-- lighthouse-finding: … -->`).
- Deduplication reads every issue with the `lighthouse` label, open and closed, and matches the
  fingerprint. A closed issue still blocks a new one. Titles are only a secondary veto
  (similarity ≥ 0.8) for issues created before fingerprints existed; a title never creates a
  finding on its own.
- The actionability gate refuses a finding unless `repo_evidence.file` exists in the repository
  and `repo_evidence.symbol` occurs in that file, so host and platform noise cannot become an
  issue. It also refuses an audit id or route that is absent from the digest: `build` writes
  `audits.json` next to `context.md`, and `publish-preview`/`publish-create` validate every
  finding against it, so a fabricated audit cannot be filed even with real repository evidence.
- Labels for real findings: `lighthouse`, the category (`performance`, `accessibility`, `seo`,
  `best-practices`) and `bug` (or `enhancement` for `low`). At most three real issues are
  created per run.
- `publish-create` repeats the deduplication read before each create call. If an issue appeared
  after the preview, the finding is recorded as `duplicate_after_preview` and nothing is
  created. A failed preview skips creation entirely (fail closed), while the reports and the
  preview artifact are still uploaded.

### Test mode

`workflow_dispatch` with `test_mode=true` demonstrates the whole pipeline without falsifying
data:

- The real Lighthouse audit still runs and its reports stay byte-identical; the synthetic
  finding is injected into `context.md` from `scripts/lighthouse-test-fixture.mjs`.
- The fixture goes through the same agent analysis, validation, deduplication and publishing
  path. If the model drops it, the canonical fixture is still published and
  `agent_included_test_finding: false` is recorded.
- The issue is titled `[TEST] …`, carries only the `lighthouse-test` label and explains that it
  is synthetic and not a Lighthouse result.
- The fingerprint is frozen (`582f378dfa6c0628`), so a second test run finds the existing issue
  and records a duplicate instead of creating another one.
- Test mode never publishes real findings: they are analysed and listed as `suppressed` in
  `decisions.md`.
- `create_issues=false` turns the run into a dry run: `proposed-issue.md` shows the exact title,
  labels and body, and `decisions.md` records whether the issue would be created or skipped as a
  duplicate.
- The synthetic issue is a permanent deduplication record. Close it after the demonstration; it
  is never reopened or deleted automatically. No comments are added to it, so a maintainer who
  wants a fresh demonstration can delete it and re-run the workflow manually.

The test-mode decision and outcome are written to `decisions.md` and to the Actions step
summary. Scheduled runs cannot reach test mode: the normalisation step rejects it, and the
scripts throw when `GITHUB_EVENT_NAME` is not `workflow_dispatch`.

### Prerequisites and artifacts

One-time setup, done by the repository owner:

```bash
gh variable set APP_URL --body https://cal-clone-gqib.onrender.com
gh label create lighthouse --color 0E8A16 --description "Finding from the scheduled Lighthouse audit"
gh label create lighthouse-test --color FBCA04 --description "Synthetic Lighthouse test finding; safe to close or delete"
gh label create performance --color 1D76DB
gh label create seo --color 5319E7
gh label create best-practices --color 0052CC
```

`accessibility`, `bug` and `enhancement` already exist. The workflow needs the
`OPENCODE_API_KEY` secret that the other agent workflows use.

| Artifact | Contents | Retention |
| --- | --- | --- |
| `lighthouse-reports` | `landing.report.json`, `landing.report.html`, `meta.json` | `retention_days`, default 30 |
| `lighthouse-analysis` | `context.md`, `prompt.md`, `provenance.json`, `events.jsonl`, `opencode.log`, `report.md`, `findings.json` | `retention_days`, default 30 |
| `lighthouse-preview` | `decisions.md`, `issues.md`, `proposed-issue.md` | fixed 15 days |
| `lighthouse-issues` | the same files after creation, with issue links | fixed 15 days |

Limitations: performance scores on the free Render plan are noisy (shared CPU, sleeping,
Cloudflare edge), so the workflow reports them as a trend and does not fail on a score drop;
issues are not attributed to a specific commit because the deployed image does not expose its
SHA, and the deployed build can lag `main` by one auto-deploy cycle. The audit is advisory: a
human still decides whether a finding is worth a ticket.

## Run the gates locally

```bash
mise install            # install the pinned toolchain once
mise run setup          # install dependencies and regenerate the SDK

mise run lint           # lint
mise run typecheck      # types
mise run test           # backend unit + backend e2e + frontend
mise run test:e2e       # backend e2e only (independent)
mise run e2e:golden     # Playwright browser scenarios (also part of `check`)
mise run build          # backend build + frontend build
mise run docker:build   # production Docker image (also a separate PR job in CI)
mise run check:sdk      # generated SDK freshness
mise run check:versions # single-version drift across workspace packages
mise run check:release-please # release-please config matches the single version
mise run check:ci       # workflow/config validation
mise run check          # everything above, exactly what CI runs
```

Individual package commands remain available: `pnpm --filter backend test:e2e`,
`pnpm --filter backend build`, `pnpm --filter frontend build`, etc.

The Playwright browser scenarios (`mise run e2e:golden`) are part of `mise run check`, so they
run both locally and in CI with the real backend and frontend and a dedicated SQLite database.
They use dedicated ports `3100` (API) and `5273` (frontend), so they do not collide with the
dev servers on `3000`/`5173`. Their TypeScript and scripts are also covered offline: `lint`
runs oxlint over `e2e/`, `playwright.config.ts` and `scripts/`, and `typecheck` runs
`tsc -p tsconfig.e2e.json`. They are documented in
[architecture.md](architecture.md#testing).

## Required status check / branch protection

The required check is applied on `main` (the repository's default branch). Configured
with the GitHub CLI:

```bash
gh api --method PUT repos/{owner}/{repo}/branches/main/protection --input - <<'JSON'
{
  "required_status_checks": {
    "strict": true,
    "contexts": ["check"]
  },
  "enforce_admins": true,
  "required_pull_request_reviews": null,
  "restrictions": null,
  "allow_force_pushes": false,
  "allow_deletions": false,
  "required_conversation_resolution": true
}
JSON
```

Verify it:

```bash
gh api repos/{owner}/{repo}/branches/main/protection \
  --jq '{checks: .required_status_checks.contexts, strict: .required_status_checks.strict, enforce_admins: .enforce_admins.enabled}'
```

`check` is the workflow/job name from `check.yml`; if the job is renamed, update the
required context too. The protection requires admin permission on the repository — if
the API answers `403`, the repository owner must run the command above.

The `docker` job is deliberately **not** a required status check: it only guards the
production artifact, and a red image build must not block merging unrelated fixes. Treat it
as a signal — if GitHub reports a failing `docker` check on a PR, fix or explicitly discuss
it before merging.

`integration/call-calendar` is currently a local integration branch and is not pushed
to `origin`. If it becomes a remote branch that receives PRs, protect it with the same
payload and `branches/integration%2Fcall-calendar/protection` in the URL.
