# AGENTS.md

## Overview

Cal.com-like booking calendar (Hexlet student project). pnpm monorepo, Russian-language docs/spec.

- `apps/backend` — NestJS 12 (ESM), Vitest, oxlint
- `apps/frontend` — React 19 + Vite + Tailwind CSS 4 + shadcn, Vitest + Testing Library
- `typespec` — TypeSpec API spec, compiles to `tsp-output/.../openapi.yaml`
- `packages/api-client` — typed SDK generated by `@hey-api/openapi-ts` into `src/client/`

How the pieces fit — request flow, backend layers, domain rules, data/migrations, the
TypeSpec → SDK pipeline and deployment: [`docs/architecture.md`](docs/architecture.md). Read it
before changing how modules, endpoints or the database are wired.

Generated paths — never hand-edit; both are regenerated by `pnpm generate:api` and are gitignored:

- `typespec/tsp-output/` — generated OpenAPI from `typespec/main.tsp`
- `packages/api-client/src/client/` — generated TypeScript SDK from that OpenAPI

No suitable NestJS server-code generator is configured, so backend controllers are hand-written
and kept in sync with the contract by the API e2e tests.

## Toolchain

All tools (Node 22, pnpm 10, hk, pitchfork) are pinned in `mise.toml`. Install via `mise install`, then `mise run setup` (installs deps + generates SDK). Run tasks through `mise run <task>` rather than calling pnpm scripts directly when a task exists.

## Key commands

- `mise run dev:backend` / `mise run dev:frontend` — dev servers (ports 3000 / 5173)
- `mise daemons start` — both dev servers as background daemons (pitchfork); also `ls` / `logs` / `stop`
- `mise run check` — the full gate: lint + typecheck + tests (unit + e2e) + the real-server browser scenarios + build + SDK freshness + single-version drift + CI config validation. **This is what CI runs; make it pass before finishing any change.**
- `mise run build` / `mise run test:e2e` / `mise run e2e:golden` — build both apps / run backend e2e tests / run the browser scenarios independently.
- `mise run docker:build` — build the production image (`cal-clone:local`); CI runs it as the separate `docker` job on pull requests.
- `pnpm generate:api` — recompile TypeSpec and regenerate the SDK. Required after touching `typespec/`; `mise run check` fails with a diff if the generated client is stale.

## Testing

- Backend: `pnpm --filter backend test` (vitest run). Single file: `pnpm --filter backend exec vitest run <file>`. E2E: `pnpm --filter backend test:e2e` (separate config `vitest.config.e2e.ts`).
- Frontend: `pnpm --filter frontend test`; single file the same way with `exec vitest run <file>`.
- Root `pnpm test:backend` / `pnpm test:e2e` / `pnpm test:frontend` run suites sequentially; `mise run test` = backend unit + backend e2e + frontend.

## Git conventions

Git hooks are managed by [hk](https://hk.jdx.dev/) (`hk.pkl`):

- `pre-commit` — lint
- `pre-push` — full `mise run check`
- `commit-msg` — **Conventional Commits enforced**: messages must match `type(optional-scope): description`, e.g. `feat: add booking endpoint`, `fix(slots): exclude occupied intervals`. Valid types: `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, `revert`. Non-conforming messages are rejected. The implementation commit references the ticket it closes, for example: feat: booking an available slot (#12).

Do not bypass hooks (`--no-verify`) — CI re-runs the same checks.

## CI

- `.github/workflows/check.yml` — the single shared pipeline: `mise run setup`, Playwright browser install, then `mise run check` on every push/PR. It also builds both apps, runs backend e2e and the real-server browser scenarios (owner booking deletion and the guest golden path); no repository secrets, safe for fork PRs. A PR-only `head-browser-evidence` job checks out the exact head SHA, records and verifies `git rev-parse HEAD`, runs those two browser scenarios with `--trace on`, and uploads the `head-browser-<sha>` Actions artifact (SHA, results, traces) for the human pre-merge check. A PR-only `docker` job runs `mise run docker:build` to guard the production image.
- `.github/workflows/release-please.yml` — release automation on push to `main`: Release PR with a single project version and CHANGELOG, then a GitHub Release and `vX.Y.Z` tag after merge. See [`docs/releases.md`](docs/releases.md).
- `.github/workflows/hexlet-check.yml` — auto-generated by Hexlet; **do not edit or delete**.
- `.github/workflows/opencode.yml` — comment-driven agent: `/oc` or `/opencode` in an issue or
  pull request comment (owner/member/collaborator only) runs OpenCode on `opencode/deepseek-v4.1-flash`
  via the `OPENCODE_API_KEY` secret. Write permissions for the agent come from the OpenCode
  GitHub App over OIDC; the OpenCode step never receives the workflow token. The workflow is
  split into a `budget` job and an `opencode` job: only `budget` holds a write-scoped token
  (`actions: read` + `pull-requests: write`), and it checks out the **default branch** so the
  per-PR attempt-budget gate (`scripts/opencode-budget.mjs`) never runs pull-request-controlled
  code with a write token. That gate checks tagged Actions history before the model and posts a
  `limit_exhausted` notice; the `opencode` job keeps `contents: read` + `id-token: write`. A
  small `Check the model key` preflight fails early when `OPENCODE_API_KEY` is missing; other
  failures and timeouts are diagnosed from the Actions run log. Not part of the PR gate; see
  [`docs/ci.md`](docs/ci.md).
- `.github/workflows/issue-triage.yml` — automatic triage: every newly opened issue from an
  owner/member/collaborator (never a bot) gets one read-only OpenCode triage comment. Issues
  already labelled `ready-for-agent` are skipped, so `/to-spec` and `/to-tickets` output is
  never triaged again. Not part of the PR gate; see [`docs/ci.md`](docs/ci.md).
- `.github/workflows/review.yml` — independent advisory AI review of eligible
  same-repository PRs from trusted authors (plus `opencode-agent[bot]`; drafts and forks are
  skipped). It runs OpenCode read-only, publishes one general comment with the reviewed
  commit SHA and Actions run link, and updates that comment on later pushes. A short result
  goes to the job summary. `REVIEW.md` and `AGENTS.md` criteria come from the base branch
  only; a missing base file fails the review before the model runs. It never approves,
  rejects, merges or edits a PR and is not a required check. Criteria and report format:
  [`REVIEW.md`](REVIEW.md); setup and manual checks: [`docs/ci.md`](docs/ci.md).
- `.github/workflows/lighthouse.yml` — weekly Lighthouse audit of `vars.APP_URL` plus a
  `workflow_dispatch` demonstration. The audit writes JSON/HTML reports, hashes them, passes a
  digest to OpenCode, and publishes deduplicated issues by a stable fingerprint
  (`lighthouse` label) — at most three per run. `test_mode` is manual-only: it injects the
  frozen synthetic finding from `scripts/lighthouse-test-fixture.mjs` and publishes it as a
  `[TEST]` issue with the `lighthouse-test` label; scheduled runs cannot enable it and test
  findings never mix with real ones. Not part of the PR gate; criteria live in
  [`LIGHTHOUSE.md`](LIGHTHOUSE.md), setup and test mode in
  [`docs/ci.md`](docs/ci.md#scheduled-lighthouse-audit-lighthouseyml).
- `main` is protected: the `check` status is required (strict, admins enforced). The pipeline, local gates and the branch-protection commands are documented in [`docs/ci.md`](docs/ci.md). If a new workflow/job name replaces `check`, update the required status context.

## Deployment

- `render.yaml` — Render Blueprint for the single Docker image (`runtime: docker`, health check `/health`, `plan: free`, `autoDeployTrigger: checksPass`). The app must keep binding `$PORT` (never hardcode it); the free plan has no disk, so SQLite in `/data/app.db` is ephemeral — the paid-plan disk block is commented out, and `DATABASE_URL` must stay inside the disk mount if it is enabled. Startup goes through `docker-entrypoint.sh`, which fixes `/data` ownership and drops from root to `node`; keep that when changing the image. See [`docs/deploy.md`](docs/deploy.md).
- MCP servers are configured in `opencode.json`: `hexlet` (course tools) and `render` (hosting). Render does **not** support OAuth dynamic client registration, so the server uses header auth with `oauth: false`: put a Render API key into the `RENDER_API_KEY` environment variable (`Authorization: Bearer {env:RENDER_API_KEY}`). The server can create services, change env vars, trigger deploys, and read logs/metrics.

## Gotchas

- Linter is **oxlint**, not ESLint (backend uses `--type-aware` via `oxlint-tsgolint`).
- Frontend `typecheck` is `tsc -b` (project references), not plain `tsc --noEmit`.
- Business rules worth knowing before changing booking logic: slots are sliced from a fixed working-hours window; any time overlap with **any** booking (of any meeting type) makes a slot unavailable globally; there is no auth and no per-user timezone selection by design; no rescheduling; the Calendar Owner can delete an upcoming Booking (hard delete, the interval frees immediately; see `docs/adr/0004-deleting-bookings.md`); the owner timezone is a fixed constant (`Europe/Moscow`, see `docs/adr/0003-owner-timezone-and-booking-horizon.md` and README).
- The `/oc` agent has a per-PR attempt budget derived from GitHub Actions run history tagged by `run-name: opencode ref-<N>`. The gate is `scripts/opencode-budget.mjs` with unit tests in `scripts/opencode-budget.test.mjs`; guard tests in `scripts/ci-config.test.mjs` run as part of `mise run check:ci`. Do not rename the workflow or the `run-name` prefix, and do not add a comment command that resets the budget: both silently reset the history-based counter. `/oc` on a plain issue is not budgeted. Keep the gate in the separate `budget` job: it is the only place with a write-scoped token and it checks out the default branch, because `pull_request_review_comment` would otherwise run pull-request-controlled code from `scripts/opencode-budget.mjs` with that token.
- `.github/workflows/**` is off limits for the `/oc` agent: the OpenCode GitHub App has no `workflows` permission (an installation cannot grant what the App does not request), and GitHub rejects any App push that touches a workflow file. `opencode.yml` therefore denies `edit` for that path, and an agent that thinks CI needs a change must describe it in its comment for a human to apply. Do not remove that deny rule, and do not work around it with a shell write.
